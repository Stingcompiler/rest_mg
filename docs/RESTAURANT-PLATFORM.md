# منصة المطعم — الأصناف الديناميكية وتجربة الطلب العام

خطة على مراحل. **المرحلة ١ (الأساس، Backend) مكتملة ومُختبَرة.** بقية المراحل
واجهات أمامية تُبنى فوق هذا الأساس دون أي تغيير كاسر.

## المرحلة ١ — أساس الـBackend ✅ (مكتملة)

كلها إضافية (additive)؛ لم يُعد كتابة أو كسر أي عقد API قائم.

- **صور الأصناف**: حقل `image` (ImageField، رفع فعلي) على `MenuItem`، مع
  `MEDIA_ROOT`/`MEDIA_URL` ومسار يخدم الملفات من نفس الـmonolith. الرفع عبر
  إجراء مخصّص `POST /catalog/items/{id}/image` (multipart)، ويعيد الـserializer
  `image_url` مطلقًا. Pillow أُضيف إلى requirements.
- **الأصناف المميّزة**: حقل `is_featured` على `MenuItem`، يظهر في قسم `featured`
  في الـAPI العام.
- **صلاحية الكاشير على الكتالوج**: صلاحية جديدة `IsCatalogEditor` (المالك،
  المدير، **والكاشير**) حلّت محل `IsManager` على كتالوج الأصناف والتصنيفات —
  توسيع بدور واحد، لا استبدال لنموذج الصلاحيات. المطبخ لا يُدير الأصناف.
- **طلب توصيل عام**: `POST /api/v1/public/order/` (بدون مصادقة). **السعر يُحسب
  من قاعدة البيانات لا من العميل**؛ الطلب يحمل معرّفات الأصناف والكميات فقط،
  والاسم والسعر يُلتقطان من `MenuItem`. الأصناف غير المتاحة أو المجهولة تُرفض
  (409)، والإجمالي يُحسب server-side ويُعاد في التأكيد.
- **حقول الطلب**: على `Order` (كلها nullable، لا تمسّ طلبات الـPOS):
  `channel` (pos/online)، `delivery_status` (pending→confirmed→preparing→
  out_for_delivery→delivered/cancelled)، و`customer_name/phone/address/area/notes`.
- الطلب العام يُولَد كـ`Order` عادي (delivery, sent, kitchen=queued)، فيظهر
  تلقائيًا في **قائمة طلبات المدير وعلى شاشة المطبخ** عبر المسارات القائمة.

**التحقق**: ٩٤ اختبار Django ينجح (١٣ جديدًا)، والفحص الحيّ يُثبت السلسلة كاملة:
طلب عام #3008 (٣×شاورما = 37500، مُسعّر server-side) ظهر في قائمة المدير وعلى
لوحة المطبخ `[queued] 3x شاورما لحم`.

## المراحل التالية (واجهات أمامية، فوق هذا الأساس)

**المرحلة ٢ — إدارة الأصناف في الواجهة** ✅ (مكتملة): شاشة كتالوج واحدة مشتركة
`/catalog` يصل إليها المدير والكاشير (حارس RequireRole يسمح owner/manager/cashier،
والخادم يفرض `IsCatalogEditor`). تدير التصنيفات (إضافة/تعديل/تعطيل) والأصناف
(إضافة/تعديل/حذف، اسم عربي/إنجليزي، وصف، سعر، تصنيف)، مع **مفتاحَي التوفّر
والمميّز مباشرة على البطاقة**، و**رفع صورة فعلي** (multipart). تُبنى على الـAPI
الأونلاين (TanStack Query) — لا نسخة ثانية. Mobile-first وRTL؛ المحرّر sheet على
الهاتف. مرتبطة من قائمة المدير الجانبية ومن شاشة قائمة الكاشير (`/pos/menu`).

التحقق الحيّ (كـ**كاشير**): أنشأ صنفًا "فتة الطاسة"، فعّل "مميّز" فظهر فورًا في
`featured` بالـAPI العام (**مصدر حقيقة واحد**)، رفع صورة PNG فخُدِمت من
`/media/...` وظهر رابطها في الـAPI العام، وأنشأ تصنيفًا (201). المدير يرى المدخل
"الأصناف" في قائمته الجانبية. ١١١ اختبار web ينجح، tsc وlint نظيفان.

**المرحلة ٣ — صفحة هبوط احترافية** ✅ (مكتملة): أُعيد تصميم `LandingClient`
بالكامل كموقع مطعم حقيقي، من الـAPI العام (مصدر واحد):
- **شريط علوي ثابت** (اسم + "اطلب الآن").
- **Hero** بصورة كاملة (من `photos`، أو تدرّج لوني عند غيابها) + طبقة تعتيم +
  اسم + عنوان تسويقي + زرَّي "اطلب الآن"/"تصفح القائمة".
- **قسم المميّزة** (`featured`) بطاقات أفقية.
- **قائمة ديناميكية** بفلترة بالتصنيفات (شرائح "الكل" + كل تصنيف من الـAPI،
  فلترة client-side)، بطاقات بصورة/سعر/وصف/شارة "نفد" عند عدم التوفّر.
- **"لماذا نحن؟"** ست بطاقات مميّزات بأيقونات.
- **قسم الطلب + معلومات المطعم** (عن المطعم، العنوان، الخريطة، الساعات) وأزرار
  طلب عبر واتساب/الاتصال (روابط فعلية).
- **Footer** احترافي (اسم، وصف، روابط، تواصل، حقوق).
- Mobile-first، RTL، theme-aware، مع Skeleton loader وحالات فراغ/خطأ.

التحقق الحيّ: كل الأقسام تظهر، الفلترة تعمل (١٣ صنف → مشروبات ٢ → الكل ١٣)،
روابط واتساب/الاتصال فعّالة، بلا تمرير أفقي على الهاتف (شبكة عمود واحد) ولا على
الحاسوب. tsc/lint/بناء نظيف، ١١١ اختبار web ينجح.

روابط "اطلب"/"أضف" حاليًا تُمرّر إلى قسم الطلب (واتساب/اتصال فعليان)؛ سلة الطلب
داخل الصفحة تأتي في المرحلة ٤.

**المرحلة ٤ — تجربة الطلب العام** ✅ (مكتملة): `OrderFlow.tsx` — سلة في الصفحة
عبر Context، وأزرار "أضف" في بطاقات القائمة والمميّزة تضيف فعليًا:
- **سلة**: شريط عائم يظهر عند وجود أصناف (عدد + إجمالي)، وsheet يعرض السطور مع
  زيادة/إنقاص الكمية والحذف والمجموع.
- **نموذج التوصيل**: الاسم، الهاتف، العنوان، المنطقة، ملاحظات — مع تحقق (الاسم/
  الهاتف/العنوان مطلوبة).
- **الإرسال** إلى `/public/order/` (السعر يُحسب server-side)، مع حالات إرسال/خطأ
  (409 = صنف غير متوفر).
- **تأكيد**: "تم استلام طلبك بنجاح 🎉" + رقم الطلب.
- خطوات cart → form → done داخل نفس الـsheet. Mobile-first، RTL، أرقام عربية.

التحقق الحيّ end-to-end: أضاف زائر شاورما دجاج ×٢ + شاورما لحم ×١ (سلة ٣٢٬٥٠٠) →
أتمّ الطلب → ملأ بيانات التوصيل → أُرسل → تأكيد **#3009** → ظهر في POS المدير
(delivery/sent/32500، مطابق للسعر server-side). على الهاتف: الشريط ملء العرض
أسفل الشاشة، الـsheet يفتح عند الإضافة، بلا تمرير أفقي. ١١١ web + ٩٤ Django ينجح،
tsc/lint نظيف.

**التدفّق الكامل مُغلق الآن**: اكتشاف → تصفّح بفلترة → إضافة للسلة → بيانات
التوصيل → إرسال → تأكيد → الطلب في POS/المدير والمطبخ.

**المرحلة ٥ — إدارة حالة التوصيل** ✅ (مكتملة): شاشة `/deliveries` مشتركة
(owner/manager/cashier عبر `IsOrderProcessor`):
- **عرض بيانات العميل** على كل بطاقة: الاسم، الهاتف (رابط اتصال)، العنوان،
  المنطقة، الملاحظات، والأصناف والإجمالي والوقت.
- **تحديث الحالة** خطوة واحدة كل مرة عبر حارس انتقالات في الخادم: قيد الانتظار →
  تم التأكيد → قيد التحضير → خرج للتوصيل → تم التوصيل، مع **إلغاء** متاح حتى
  التسليم. السجل المالي لا يُمسّ إطلاقًا — يتحرك `delivery_status` فقط.
- الطلبات المكتملة/الملغاة تنتقل إلى قسم "المكتملة" القابل للطيّ.
- **Backend additive**: حقول العميل + `delivery_status` + `channel` +
  `kitchen_status` في `OrderReadSerializer`، إجراء `delivery-status` (بحارس
  انتقالات: تخطّي غير مسموح 409)، وإجراء `deliveries` يعرض طلبات الأونلاين فقط
  (الكاشير لا يرى قائمة الطلبات الكاملة). القائمة العامة تبقى للمدير فقط.

التحقق الحيّ (كـ**كاشير**): رأى ٣ طلبات توصيل ببيانات العملاء، ونقل طلبًا عبر
الدورة الكاملة قيد الانتظار → تأكيد → تحضير → خرج → تم التوصيل، فانتقل للمكتملة
وتقدّم الطابور للطلب التالي. ١٤ اختبار Django جديد (٪الدور + الانتقالات + العزل)،
١٠٣ Django + ١١١ web ينجح، tsc/lint نظيف.

**اكتملت المنصة**: التصنيفات/الأصناف ديناميكية بالكامل، مصدر حقيقة واحد، صفحة
هبوط احترافية، وتدفّق طلب توصيل من التصفّح حتى التسليم — بالكامل عبر أدوار
وصلاحيات النظام القائمة، دون كسر أي وظيفة.

## ملاحظات سلامة (§17) — مطبَّقة في المرحلة ١

- الأسعار من الـBackend، وتُلتقط على سطر الطلب وقت الإنشاء.
- الأصناف غير المتاحة لا يمكن طلبها (تحقق server-side).
- العميل لا يستطيع تعديل السعر أو الإجمالي (يُتجاهَل أي سعر مُرسَل).
- الصلاحيات على الـBackend، لا مجرد إخفاء أزرار.
